# `ns.f = function` と `obj.cb = function` は何が違うのか

<!-- graph: sample-bindings; view: 3d; labels: all; highlight: namespace.js -->

形は同じです。

```js
d3.scale.linear = function () { … };   // これは宣言
el.onclick      = function () { … };   // これは違う
```

片方は「名前空間に関数を定義している」、もう片方は「コールバックを登録している」と、私たちはすぐに言い分けます。しかしその言い分けに使った語——名前空間、インスタンス、コールバック——はどれも**意味**の語です。第2章のテストにかけてみましょう。識別子をすべて `a1`、`a2` に置き換えたら、`a1.a2.a3 = function` と `a4.a5 = function` のどちらが名前空間か、あなたはもう言えない。

だから構造の側に、名前を読まずに決まる事実を探す必要があります。事実は二つあります。

## 事実1：その代入はいつ走るか

`d3.scale.linear = …` はモジュールが読み込まれた瞬間に、一回、無条件に走ります。理論篇 §4 の言葉では**定義時**——モジュールという `letrec` の一部です。

`el.onclick = …` は `setup(el)` が呼ばれたときに走ります。何度も走るかもしれないし、一度も走らないかもしれない。**使用時**です。

判定は機械的です。その文とモジュールの根の間に λ（関数の境界）が一つでもあれば使用時、なければ定義時。

## 事実2：他のコードがそれを名前で呼べるか

`d3.scale.linear(...)` と書けば、別のファイルからこの関数を**名指しで**呼べます。受け手 `d3.scale` が、モジュールレベルの束縛（あるいは未宣言のグローバル）から名前だけで辿れる**パス**だからです。

`el.onclick` は名指しできません。`el` は引数で、実行時に届く値です。この関数に到達する静的な名前は、プログラムのどこにも存在しない。ブラウザは値の流れを追ってこの関数に届くのであって、名前によってではない。

この事実が決定的なのは、グラフのノードが「出現（occurrence）の標的になれるもの」だからです。理論篇の定義1は、出現に**名前**を要求します。名前のないものは、辺の先になれない。

## 二つの事実で四つのマス

| | 名前で辿れる受け手 | 実行時の値の受け手 |
|---|---|---|
| **定義時** | **宣言**。`ns.f`、`X.prototype.m`、`exports.f`。ES5 綴りの `export` とクラスメソッド | 稀。格納 |
| **使用時** | **遅延束縛**。`init()` の中の `app.handler = function`。名指しできるが、`init` が走るまで存在しない | **格納**。`el.onclick`。クロージャがスロットへ逃げ、呼び出し元は値の流れでしか見つからない |

どのマスに落ちるかは、識別子を全部無意味にしても動きません。いつ走るかは構文位置で、受け手が名前で辿れるかは束縛の構造で決まり、どちらも綴りを読まないからです。

> **「名前空間」とは、定義時にしかプロパティを書かれないオブジェクトに、私たちが後から付けた名前にすぎない。**

意味の語が、構造の事実から導かれる。この順序が、この記事全体で繰り返し使う型です。

## 四つのマスを、実際のグラフで見る

右のグラフは、このマスごとに一ファイルずつ書いた小さなプログラム（`samples/bindings/`）を、本物の解析器に通した結果です。手で描いた図ではありません。

**宣言（`namespace.js`）**
`chart` はプログラムのどこにも宣言されていないグローバルです。それでも `chart.scale = {}` と `chart.scale.linear = function` は、読み込み時に名前のあるスロットを束縛するので、`chart.scale`（変数）と `chart.scale.linear`（関数、親は `chart.scale`）というノードになります。`main` から `linear` への実線が `call`、`chart.scale` への辺が `reference`。d3 v3 はこの書き方で 146 個の公開 API を定義していて、解析器がこの規則を持つ前は、そのすべてが「モジュールの雑多なコード」に溶けて見えませんでした。

**宣言、ES5 のクラス（`prototype.js`）**
`proto.isValid = function` はクラス本体の外に書かれたメソッドで、`Moment.isValid` というノードになります。`Moment.utc = function` は static メンバー。そして `proto.add = add`——これは**エイリアス**です。宣言済みの関数 `add` を指す名前がもう一つ増えただけなので、新しいノードは作らず、`add` が `Moment` のメンバーの役を得る。グラフでは `add` は床にただ一つあり、`isValid → add` の `call` がそこに刺さっています。`import` の扱いと同じです。

**遅延束縛（`late.js`）**
`app.handler` はノードとして存在し、`tick` を呼びます。しかし辺の種類が違う。`init → handler` は `reference`——`init` は `handler` を呼ぶのではなく**設置する**。`route → handler` が `call`。そして `route` が `init` より先に走れば、`app.handler` は未定義です。理論篇 §4 の初期化ハザードが、別の衣装で現れている。

**格納（`store.js`）**
`el.onclick = function` にも、最上位の `list[0].f = function` にも、ノードはありません。`onclick` も `f` も名前ではないからです。クロージャの本体が参照するもの——ここでは `save`——は、包含する宣言の辺になります。`setup → save`、そして最上位の格納は茶色の `module` ノードから `save` へ。関数はスロットへ逃げ、誰がそれを呼ぶかは値の流れ（制御フロー解析）でしか分からない。

一本だけ**破線**の辺があります。`main` から `isValid` への辺です。`m.isValid()` の `m` は型が取れないので、解析器は「同名のインスタンスメンバーすべて」に解決しました。これは過大近似なので `inferred` の印が付き、破線で描かれます。解析器が推測した辺と、ソースに書かれた辺を、絵の上で区別しているのです。

## 同じ区別が、クラスとオブジェクトを分ける

```js
class Moment {
  constructor() {
    this.onChange = () => {};              // 格納 — new のたびに別のクロージャ
  }
  add(n) { /* … */ }                        // 宣言 — class 文が走るとき一度
}
Moment.prototype.subtract = function () {}; // 宣言 — add と同じマス
proto.abs = abs;                             // エイリアス — abs がメンバーの役を得る
```

prototype（クラス、名前空間）に置かれたものは、読み込み時に一度だけ宣言される。Cook の言い方なら生成子 `gen_C` の中身です。インスタンスに置かれたものは、構築のたびに格納される。`fix(gen_C)` の結果に後から書かれるもの。第1章で「クラスとオブジェクトの関係」と呼んだものは、操作的にはこの一つの区別です。

## 正直な注記

二つ。

灰色域——使用時に名前付きスロットへ書く遅延束縛——を「宣言」として扱うのは、計算体系から導かれる結論ではなく**設計判断**です。格納として扱う選択もありえた。私たちは、名指しできるものは辺の先になれるべきだと考え、フラグで見分けられる形で宣言側に置きました。

「識別子を全部無意味にしてもマスは動かない」は、**あなたが付けた識別子**については成り立ちます。ただし `prototype`、`exports`、`module.exports`、`Object.assign` の四語は言語とプラットフォームの規約なので、解析器はこれらを綴りで特別扱いしています。構造の判定が完全に名前から自由なのではなく、規約として固定された名前にだけ依存している、というのが正確な言い方です。
